# Architecture

`cap-mcp-bridge` turns any SAP CAP / OData v4 service into a set of MCP tools, driven entirely by
the service's `$metadata`. This document explains the layering, the one data contract everything
hangs off, and the design decisions that were not obvious.

## Layers

```
src/
  metadata/   $metadata (EDMX) → ServiceModel          knows XML, knows nothing about MCP or HTTP verbs
  odata/      ServiceModel + intent → HTTP request      knows OData URL conventions, auth, retries, paging
  tools/      ServiceModel → MCP tools + resources      knows MCP shapes, knows nothing about XML or fetch
  server/     wiring, transports, config → server       glue only
  util/       logger, errors, glob matching
```

Dependencies point downwards only: `server → tools → odata → metadata`. `metadata` has no imports from
the other layers. `tools` never builds a URL; `odata` never builds a tool description. This is what
lets a new CAP service work with zero code changes: the only input is XML, and every layer above is
generic over the `ServiceModel`.

## The contract: `ServiceModel`

Defined in `src/metadata/model.ts`. It is the *only* thing the upper layers see. It is deliberately
denormalised: each `EntitySet` carries its resolved keys, properties and navigations (including
inherited ones from `BaseType`) so consumers never have to walk type hierarchies. `entityTypes` is
still present so expanded navigation targets can be typed (needed for validation and redaction).

Annotations are folded into plain fields on the model (`label`, `description`, `readOnly`,
`mandatory`, `sensitive`, `capabilities`). The parser is the only place that knows vocabulary term
names; upper layers just read booleans and strings.

## EDM → JSON Schema mapping

One table in `src/metadata/types.ts`. Notable choices:

| EDM | JSON Schema | Why |
|---|---|---|
| `Edm.Decimal` | `string` | CAP serialises decimals as strings to avoid float loss. The generated field description says so. |
| `Edm.Guid` | `string` / `uuid` | Bare (unquoted) in URL literals, quoted in JSON. The literal formatter handles this. |
| `Edm.Int64` | `integer` | Per spec. Note CAP may serialise Int64 as string when `ieee754compatible` is on; passthrough data is not touched. |
| `Edm.Date` / `DateTimeOffset` | `string` + `date` / `date-time` | Literals are bare in URLs, so the formatter never quotes them. |
| enum types | zod enum of member names | OData v4 enum literal syntax is `ns.Type'Member'`, generated by the formatter. |

The same table drives three things: tool input schemas, `describe_entity` output, and literal
formatting/validation in `$filter`. One source of truth, so they cannot disagree.

## Tool generation strategy

A real CAP service has 40+ entity sets. Four tools per set would be 160+ tools, which no client
handles well. So the default is a fixed set of **generic** tools whose *schema* is discoverable
(`list_entity_sets`, `describe_entity`, MCP resources at `cap://entity/{name}`), and the workhorse
`query_entity` takes the entity set as a parameter.

`toolMode: "auto"` switches to **typed per-entity** tools when the service has ≤ 12 entity sets.
Typed tools (`query_Books` with `select` as an enum of real property names, `orderBy.field` limited
to sortable fields) are easier for a model to call correctly, and the tool budget is affordable at
that size. Generic tools are still registered in per-entity mode for functions/actions/refresh.

Write tools (`create_entity`, `update_entity`, `delete_entity`, `invoke_action`) are only registered
when `writeEnabled` is true. They are not registered-but-disabled; they do not exist.

## The filter problem

Both the structured filter object and a raw `$filter` string are parsed into the same AST
(`src/odata/filter/ast.ts`). Raw strings go through a small recursive-descent parser
(`src/odata/filter/parse.ts`) that understands comparisons, `and/or/not`, parentheses, `in`, and the
common OData functions. The AST is then validated (`src/odata/validate.ts`) against the entity's
schema and serialised back to OData syntax. Because the serialiser owns literal quoting, the model
never has to get quoting right; it only has to name a field and a value.

Validation errors are structured: they name the offending field, what was wrong with it, and the
list of valid alternatives. This is the single biggest lever on whether an LLM self-corrects.

**Drafts.** CAP draft-enabled entities carry both the active and draft row for every record. Unless
the caller passes `includeDrafts: true`, the query builder ANDs `IsActiveEntity eq true` into the
filter. Without this, every query returns duplicates.

## Auth

`AuthProvider` is a one-method interface (`headers()`), so transports and the HTTP client never see
credentials. `oauth2-cc` keeps one in-flight token promise so concurrent tool calls cannot stampede
the token endpoint, and refreshes 60s before expiry.

## Safety rails

All in `src/odata/` and `src/tools/`, all configurable, all on by default:

- read-only unless `writeEnabled`
- `$top` default 25, hard cap 200, `$count=true` always, `nextSkip` when truncated
- ~50KB response ceiling, rows dropped from the end with an explicit note
- entity allow/deny lists (exact or glob)
- field redaction: configured names/globs plus anything annotated `@PersonalData.IsPotentiallySensitive`
- 30s timeout; retry with backoff on 5xx/429 only; never retry a write; never retry a 4xx
- logs go to stderr (stdout is the stdio transport) and never include tokens or query strings

## Transports

`createBridgeServer(config)` is a factory that builds a fully wired `McpServer`. `stdio` calls it
once. Streamable HTTP creates one server per session from the same factory, because an MCP `Server`
instance binds to exactly one transport. The `ServiceModel` cache and the auth provider are shared
across sessions so metadata is fetched once, not once per client.

## Decisions taken without a spec line

- **Record counts in `list_entity_sets`** are fetched from each set's `/$count` endpoint (with the
  draft guard applied), eight at a time, and fail soft to `null`. They are on by default (`includeCounts`) because the spec asks for them,
  but a caller can turn them off for a slow service.
- **Raw `$filter` is parsed, not regex-scanned.** A regex would miss operator/type mismatches. The
  parser covers the OData subset a model realistically emits; anything it cannot parse is rejected
  with the parse position rather than forwarded.
- **Expanded navigations are redacted type-aware.** Redaction walks the response using the
  navigation target types so a sensitive field on `Customer` is redacted inside `Orders?$expand=Customer`.
- **Config precedence** is CLI flags > environment > `cap-mcp.config.json` > defaults.
- **Int64 stays `integer`** in schemas per the spec, even though CAP can serialise it as a string.
